# MK6 Recursive Unit Architecture

이 문서는 MK6에서 논의 중인 차세대 기억/추상화 구조를 정리한 설계 초안이다.

## 1. 배경

현재 MK6의 LangGraph는 입력 문장을 문자 단위로 분해한 뒤, 같은 문장에서 함께 등장한 문자들의 패턴을 셀로판지처럼 겹쳐 보면서 반복되는 묶음을 찾아 단어 단위로 올리는 방향을 사용한다.

이후에는 ConceptGraph를 완전히 별도의 계층형 그래프로 설계하기보다, 같은 원리를 재귀적으로 반복해 문자 → 단어 → 의미 → 맥락 → 더 높은 개념 구조까지 확장하는 방향을 검토한다.

핵심 아이디어는 다음과 같다.

> 이전 단계에서 추출된 결과를 다시 동일한 시스템의 입력으로 넣고, 같은 방식의 패턴 추출을 반복한다.

따라서 시스템 내부에서는 "단어", "의미", "개념", "객체" 같은 타입을 미리 고정하지 않는다. 모두 이전 단위들의 반복 패턴에서 생성된 새로운 단위일 뿐이다.

---

## 2. 기본 처리 흐름

### 2.1 문자에서 단위 추출

1. 입력 문장을 문자 단위로 분해한다.
2. 각 문자는 LangGraph/Unit 저장소에서 조회하거나 생성한다.
3. 같은 문장에서 발생한 문자들은 하나의 `sentence_id`를 공유한다.
4. 동일 문장 내 문자 배열들을 여러 문장에 걸쳐 셀로판지처럼 겹쳐 반복 패턴을 찾는다.
5. 반복적으로 함께 나타나는 문자 묶음을 새로운 Unit으로 생성한다.

예시:

```text
나는 사과를 먹었다
↓
[나][는][ ][사][과][를][ ][먹][었][다]
↓ 반복 패턴 추출
[나는] [사과를] [먹었다]
```

이때 인간 기준으로는 결과를 "단어"라고 부를 수 있지만, 시스템 내부에서는 단지 더 높은 depth의 Unit이다.

### 2.2 추출된 Unit을 다시 입력

문자 단계에서 얻은 Unit들을 다시 동일한 저장소/추출 엔진에 입력한다.

중요한 점은 최초 문자 단계에서 사용한 `sentence_id`를 그대로 유지하는 것이다.

```text
sentence_id = 123

[나는]      depth=1, sentence_id=123
[사과를]    depth=1, sentence_id=123
[먹었다]    depth=1, sentence_id=123
```

이를 통해 시스템은 이 세 Unit이 같은 원문 문장에서 함께 관측되었다는 사실을 잃지 않는다.

### 2.3 다시 셀로판지 추출

같은 sentence_id 안에서 함께 나타난 depth 1 Unit들을 여러 문장에 걸쳐 다시 겹쳐 본다.

예를 들어:

```text
나는 사과를 먹었다
나는 밥을 먹었다
나는 빵을 먹었다
```

이 반복 관측에서 시스템은 다음과 같은 상위 패턴을 만들 수 있다.

```text
[나는] + [X] + [먹었다]
```

이 결과 역시 별도의 "의미 타입"으로 취급하지 않고 새로운 Unit으로 저장한다.

필요하면 이 Unit을 다시 같은 추출 엔진에 넣어 더 높은 맥락이나 개념 구조를 유도한다.

## 3. Unit과 depth

모든 내부 표현을 `Unit`이라는 하나의 개념으로 통일한다.

### 3.1 depth 정의

- `depth = 0`: 문자
- 그 이후 새 Unit의 depth는 자신을 구성한 Unit들 중 가장 높은 depth에 1을 더한다.

공식:

```text
new_depth = max(child.depth) + 1
```

예시:

```text
0 + 0 -> 1
1 + 1 -> 2
1 + 2 -> 3
0 + 3 -> 4
2 + 2 + 4 -> 5
```

따라서 depth는 "언어학적 단계"가 아니다.

예를 들어 다음처럼 고정하지 않는다.

```text
1 = 단어
2 = 의미
3 = 개념
4 = 객체
```

대신 depth는 다음만 나타낸다.

> 원시 문자(depth 0)로부터 몇 단계의 추출/합성 구조 위에서 만들어졌는가.

서로 다른 depth의 Unit이 합쳐져 더 높은 Unit을 만드는 것도 허용한다.

```text
A(depth 1) + B(depth 2)
        ↓
      C(depth 3)
```

A의 관점에서는 depth 1에서 depth 3으로 직접 연결되어 보이지만, 이는 중간 depth를 건너뛴 오류가 아니라 깊이가 다른 두 가지가 depth 3에서 합류한 것이다.

## 4. 생성 계보

`depth`만으로는 Unit의 실제 의미와 생성 과정을 설명할 수 없기 때문에, 모든 Unit은 자신을 구성한 하위 Unit들의 계보를 보존해야 한다.

예시:

```text
u100 (depth 1)
made_from:
- u001 "사"
- u002 "과"
```

그리고:

```text
u200 (depth 2)
made_from:
- u110 "나는"
- u120 "사과를"
- u130 "먹었다"
```

이 계보를 통해 어떤 고차 Unit도 최종적으로 원문 문자까지 역추적할 수 있다.

권장 최소 구조:

```text
Unit
- unit_id
- depth
- created_at
- support_count
```

```text
UnitComposition
- parent_unit_id
- child_unit_id
- position
```

```text
Occurrence
- unit_id
- sentence_id
- position
```

## 5. sentence_id의 역할

`sentence_id`는 각 단계에서 새로 만드는 것이 아니라, 최초 원문에서 발생한 동일한 출처 문맥을 계속 이어 주는 역할을 한다.

이를 통해 다음 정보가 보존된다.

- 어떤 문자들이 같은 문장에서 나왔는가
- 어떤 depth 1 Unit들이 같은 문장에서 함께 나왔는가
- 어떤 상위 Unit들이 동일한 원문 문맥에서 파생되었는가

즉 sentence_id는 단순한 문장 번호라기보다, Unit들이 함께 관측된 최초 사건/문맥의 공통 식별자 역할을 한다.

## 6. 재귀적 추출 구조

전체 구조는 다음처럼 표현할 수 있다.

```text
관측
↓
패턴 겹침
↓
Unit 발견
↓
동일한 시스템에 재입력
↺
```

좀 더 구체적으로는:

```text
문자(depth 0)
    ↓
셀로판지 패턴 추출
    ↓
Unit(depth 1)
    ↓
같은 sentence_id 단위로 재입력
    ↓
셀로판지 패턴 추출
    ↓
Unit(depth 2)
    ↓
재입력
    ↓
Unit(depth 3)
    ↓
...
```

이 구조의 핵심은 한 단계마다 별도의 전용 알고리즘을 만들지 않는 것이다.

가능하면 동일한 추출 함수가 모든 depth를 처리하도록 한다.

개념적으로는 다음과 같은 형태다.

```python
extract(units: list[Unit]) -> list[Unit]
```

## 7. ConceptGraph와의 관계

기존 구상처럼 LangGraph와 ConceptGraph를 반드시 별도의 독립 시스템으로 나눌 필요는 없다.

문자 → 단어 → 의미 → 맥락 → 개념의 경계가 데이터에 따라 자연스럽게 생기도록 한다면, 시스템 내부에서는 모두 같은 종류의 Unit으로 취급할 수 있다.

사람이 외부에서 특정 depth의 Unit을 보고 "단어", "사용 의미", "맥락", "개념"이라고 해석할 수는 있지만, 시스템 내부에서 그 이름을 필수 타입으로 고정하지 않는다.

따라서 기존 `LangGraph`라는 이름은 장기적으로 부정확해질 수 있다. 이 구조는 언어에만 국한된 그래프라기보다 반복 관측을 재귀적으로 압축하는 Unit 기반 기억/추상화 시스템에 가깝다.

## 8. Think에 대한 현재 방향

의미 단위까지 만드는 방법은 위 구조로 잡혀 가고 있지만, "생각"은 아직 설계 단계다.

현재 논의된 기본 방향은 다음과 같다.

1. 현재 입력에서 생성된 Unit을 활성화한다.
2. 기존 기억에서 공통 자식/부모, 유사한 구성 패턴, 동일한 문맥 계보를 가진 Unit들을 후보로 확장한다.
3. 여러 가능한 조합을 만든다.
4. 기존 구조를 얼마나 유지하는지, 기존 연결을 얼마나 깨뜨려야 하는지를 기준으로 후보 정합성을 비교한다.
5. 더 적은 충돌로 더 많은 기존 구조를 설명하는 조합을 우선한다.

정합성의 기본 아이디어:

```text
좋은 후보
= 현재 입력을 설명함
+ 기존 구조를 많이 유지함
+ 기존 연결을 적게 파괴함
+ 불필요한 새 연결이 적음
```

예시:

```text
후보 A
- 기존 구조 유지 10
- 새 연결 2
- 기존 연결 파괴 0

후보 B
- 기존 구조 유지 5
- 새 연결 4
- 기존 연결 파괴 3
```

이 경우 후보 A를 더 정합한 구조로 본다.

다만 실제 후보 생성 알고리즘, 정합성 점수식, 탐색 범위는 아직 결정되지 않았다.

## 9. 결과 문장 생성에 대한 현재 방향

Think 결과를 단순히 `made_from` 계보대로 역전개하면 자연스러운 문장이 된다는 보장은 없다.

같은 의미/상위 Unit이 다양한 실제 표현으로 나타날 수 있기 때문이다.

예:

```text
나는 사과를 먹었다
사과를 내가 먹었다
내가 먹은 건 사과였다
```

따라서 상위 Unit이 실제 과거 문장에서 어떤 depth 1 배열로 표현되었는지를 별도의 realization/occurrence 기록으로 유지하는 방향을 고려한다.

개념적 출력 흐름:

```text
Think 결과 Unit
↓
과거 표현 패턴 조회
↓
현재 문맥과 잘 맞는 표현 패턴 선택
↓
depth 1 Unit 배열
↓
depth 0 문자 또는 원문 surface 복원
↓
결과 문장
```

이 구조라면 언어 생성 역시 학습량이 증가할수록 자연스러워질 수 있다.

초기에는 표현 데이터가 적어 다소 거친 문장이 나오더라도, 같은 의미 구조의 실제 사용 사례가 누적되면서 더 자연스러운 realization을 선택할 수 있다.

## 10. 설계 원칙

현재까지 합의된 원칙은 다음과 같다.

- 문자만 `depth 0`이라는 명확한 시작점으로 둔다.
- 단어/의미/개념/객체 같은 상위 타입을 미리 고정하지 않는다.
- 모든 결과는 다시 동일한 추출 구조의 입력이 될 수 있다.
- Unit의 depth는 `max(child.depth) + 1`로 정의한다.
- 서로 다른 depth의 Unit 조합을 허용한다.
- 각 Unit은 생성 계보를 유지한다.
- 최초 입력의 `sentence_id`를 상위 추출에서도 유지한다.
- 상위 구조는 원문까지 역추적 가능해야 한다.
- Think와 언어 출력을 Unit 추출/기억 구조와 분리해 설계한다.

---

## 11. 미결 과제

다음 항목은 후속 설계가 필요하다.

- 셀로판지 패턴을 상위 depth Unit에 적용할 때의 정확한 비교 기준
- Unit 후보 생성 및 중복 병합 기준
- support_count 외에 필요한 신뢰도/빈도 정보
- sentence_id만으로 부족할 경우 더 큰 context/event 식별자 도입 여부
- Think 후보 생성 방식
- Think 정합성 점수식
- 기존 연결을 "파괴한다"고 판단하는 정확한 조건
- 활성화 전파 범위와 탐색 중단 조건
- 결과 문장 realization 선택 기준
- 신규 표현 생성이 필요한 경우의 처리 방법

이 문서는 구현 확정안이 아니라, MK6의 다음 방향을 정리한 RFC 성격의 설계 문서다.
